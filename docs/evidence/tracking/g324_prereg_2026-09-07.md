## Frame anchors -- G311 AMENDMENT 1's readable-anchor rule, carried verbatim

40 evenly spaced indices spanning **0 .. the LAST DECODABLE index**, that anchor
**MEASURED per clip by binary search on the real cv2 seek path**, never taken from
ffprobe's container `nb_frames`, which overcounts the seekable range by up to 132
frames on this corpus. Formula `round(i * last_decodable / 39)`, i = 0..39, no head
slice. A failed read is FATAL and aborts the game; frames are never silently
dropped. Both arms see the SAME decoded frames from the SAME decode.

G311's measured anchors, for reference only -- they are re-measured, not assumed:
`wnba_01_1080p` 18000, `ncaa_IB-_u4gW3ds_1080p` 17982, `wnba_06` 28673.

## Proxies, defined now (1-5 carried verbatim from G311's sealed prereg)

1. `boxes_per_frame` = person boxes emitted / decoded frames. Zero-box frames
   stay in the denominator and are counted and reported separately.
2. Agreement, BOTH ways, greedy one-to-one matching on IoU, threshold 0.5:
   `agree_Y_in_R` = matched Y boxes / all Y boxes; `agree_R_in_Y` = matched R
   boxes / all R boxes. Matching is per frame, boxes sorted by descending IoU,
   each box consumed at most once. The two shares differ whenever the arms emit
   different box counts; both are reported.
3. `distinct_ids` and `median_track_length` after the SAME greedy IoU-linking
   tracker applied to both arms' boxes, identical parameters for both arms.
4. `ms_per_frame` = detector call only, warm-up frames excluded.
5. `peak_vram_mb` per arm from `torch.cuda.max_memory_allocated`; both arms are
   torch models, so that is the method for both and it is stated per arm.
6. **NEW THIS ROW: `ms_per_frame_batch8`** = the same detector call over the same
   frames submitted in batches of **8** (last batch short), total elapsed / frames,
   warm-up excluded, reported BESIDE the single-image figure for BOTH arms. G311's
   single-image ARM R figure must not stand alone.

Thresholds, byte-identical to master and NOT movable: IoU match 0.5, IoU link 0.3,
detector conf 0.3, 40 frames per game, batch size 8.

## Sign convention, declared now, and restated in the verdict line

Higher `boxes_per_frame` is CONSISTENT WITH more detection. Higher agreement in
either direction is CONSISTENT WITH the two stacks seeing the same scene. Longer
`median_track_length` and fewer `distinct_ids` for the same box count are CONSISTENT
WITH steadier detections. Lower `ms_per_frame` (single-image or batch-8) and lower
`peak_vram_mb` are CONSISTENT WITH a cheaper arm and say NOTHING about detection
quality. **CONSISTENCY IS NOT EVIDENCE.**

neither arm will be declared better. The arms differ in model AND input size, so this
is a DETECTOR-STACK comparison, never a single-variable ablation. This row ADOPTS
