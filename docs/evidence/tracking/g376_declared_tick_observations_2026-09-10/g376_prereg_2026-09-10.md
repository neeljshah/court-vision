## 2. Reconstructed-schedule derivation plan

The rule is reconstructed by READING the producer and the adjudicator, and every clause is cited
`file:line` in `schedule_rule.md`. The derivation is fixed here in advance:

- DECLARED (what G370 counted): the ledger `stride` and `evaluated_frames` expanded to frame
  indices `[index * stride for index in range(evaluated_frames)]`
  (`scripts/platformkit/tracking/g370_manifest.py:31-36`). Both ledger fields are written by the
  daemon from the harness verdict (`scripts/platformkit/track_daemon.py:316-318`), where
  `evaluated_frames = len(range(0, min(decoded, stride * 30000), stride))` and
  `stride = sampling_plan(source_fps).stride`
  (`scripts/platformkit/track_daemon_done.py:141-149,203-209`;
  `scripts/platformkit/tracking_timebase.py:30-37`).
- SCHEDULED (what the producer actually evaluates): the prefetcher lattice
  `(frame_index - start_frame) % stride == 0` (`src/pipeline/unified_pipeline.py:271-278`) with the
  route stride chosen at `src/pipeline/unified_pipeline.py:1532-1533`, less every frame the
  gameplay gate rejects (`src/pipeline/unified_pipeline.py:1700` calling `_is_gameplay`,
  `:996-1036`), less every frame the non-live suspension hard-skips
  (`src/pipeline/unified_pipeline.py:1836-1853`), and truncated by the route frame cap
  (`src/pipeline/unified_pipeline.py:1536-1537,1680`; the cap reaches the run as `--frames` at
  `scripts/run_clip.py:417`).
- The producer evaluated set is OBSERVABLE per frame because `ball_tracking.csv` carries one row
  per frame that reached the tracking body, with `live = 1` on evaluated frames
  (`src/pipeline/unified_pipeline.py:1991-2001`) and `live = 0` on suspended frames
  (`src/pipeline/unified_pipeline.py:1836-1849`), while the player table gets a row only per
  surviving non-referee track (`src/pipeline/unified_pipeline.py:2657-2662`) and the evaluated
  counter increments once per evaluated frame (`src/pipeline/unified_pipeline.py:2079`, returned as
  `evaluated_frames` at `:3063`). RECONSTRUCTED SCHEDULE is therefore defined as the set of frames
  carrying a `live = 1` ball row, and its size is compared with the ledger `evaluated_frames`,
  with the route cap `max_frames // stride`, and with `ceil(decoded_frames / stride)`.
- A section whose `ball_tracking.csv` is absent, headerless, missing the `frame` or `live` column,
  or carries a non-integral frame value has NO reconstructed schedule; all its declared ticks are
  UNKNOWN. This is stated before any number so an inconvenient section cannot be dropped (B1).
- The controlled re-run (section 4a) tests this reconstruction directly against the producer own
  logged frame indices; the archival classification is not accepted on the reconstruction alone.

## 3. The four tick classes and the decision rule

Every DECLARED tick of every section is classified into exactly one class, and the four counts sum
to the declared count for every section. Let `T` be the distinct integral frame values of
`tracking_data.csv`, `E` the reconstructed schedule (ball rows with `live = 1`) and `S` the
suspended set (ball rows with `live = 0`). For declared tick `f`:

1. OBSERVED -- `f` is in `T`.
2. SCHEDULED_NO_DETECTION -- `f` is not in `T` and `f` is in `E`: the producer evaluated the frame
   and no non-referee track row survived.
3. NOT_SCHEDULED -- `f` is not in `T` and not in `E`: the declaration over-counts. The row records a
   sub-reason, decided in this order and reported as a distribution, never as a separate class:
   `SUSPENDED` (`f` in `S`), `BEYOND_ROUTE_CAP` (`f >= stride * (max_frames // stride)` for the
   route cap read from `evaluated_frame_count.json`), `OFF_PRODUCER_LATTICE`
   (`f % producer_stride != 0`), else `GATED_OR_UNREACHED`.
4. UNKNOWN -- the section has no reconstructed schedule under the section-2 rule, or `f` is not an
   integer, or a snapshot pin moved.

The bar is `>= 0.95` of declared ticks classified, i.e. UNKNOWN `<= 0.05`, over each set
separately. A tick class is decided by the reconstructed rule and the re-run, never by the
player-row count alone: OBSERVED is the only class the player table decides, and it is the class
G370 already counted.

## 4. The three controls and their exact expected values

a. RE-RUN REPRODUCTION. One fresh source is copied to `/workspace/g376_scratch/`; the DEPLOYED
   `scripts/run_clip.py` under `/workspace/deploy/nba-ai-system` is run with `--no-show`,
   `--frames 3000` and `--data-dir /workspace/g376_scratch/out`, with the evaluated frame indices
   logged. If the deployed producer offers no schedule log, the indices are captured by wrapping
   the producer from THIS lane module at import time, in the scratch run only, and the memo says
   so explicitly. EXPECTED: the set of logged evaluated indices equals the set of frames carrying a
   `live = 1` ball row in the scratch output table, exactly -- reproduction `1.0000`, symmetric
   difference `0`. Any shortfall is reported as the exact miss and fails this control.
b. FULLY OBSERVED SYNTHETIC. A synthetic section whose player table carries a row for every
   declared tick and whose ball table marks every declared tick `live = 1`. EXPECTED: OBSERVED
   `1.0000`, SCHEDULED_NO_DETECTION `0`, NOT_SCHEDULED `0`, UNKNOWN `0`, zero-observation ticks `0`.
c. DOUBLED DECLARATION. The same synthetic section with its declared `evaluated_frames` multiplied
   by exactly 2 and nothing else changed. EXPECTED: NOT_SCHEDULED share exactly `0.500000` and
   OBSERVED share exactly `0.500000`, with SCHEDULED_NO_DETECTION `0` and UNKNOWN `0`.

Controls b and c are exact equalities, not tolerances. A failed control is reported as a failed
control and downgrades the verdict to PARTIAL; no bar is lowered and no threshold is moved (Q3).

## 5. Corrected-denominator definitions

Four denominators are defined here, before measurement, and reported per section in
`consequence.csv` with the set totals in `summary.json`:

- `declared_ticks` -- the ledger expansion of section 2. This is what G370 divided by.
- `producer_evaluated_ticks` -- the reconstructed schedule size, `|E|`, the frames the producer
  actually evaluated; UNKNOWN where section 2 gives no schedule.
- `route_capped_ticks` -- `min(declared_ticks, max_frames // stride)` from the route cap in
  `evaluated_frame_count.json`, the same quantity the adjudicator already computes as
  `attempted_frames_capped` (`scripts/platformkit/track_daemon_done.py:121-138`) and does NOT carry
  into the ledger entry (`scripts/platformkit/track_daemon.py:316-318`); ABSENT where no cap exists.
- `observed_ticks` -- `|T|`, retained only as the numerator; it is never a denominator (H1).

CONSEQUENCE, computed on both sets: the G370 M1 scoring share and the G368 motion share are
restated over `producer_evaluated_ticks` beside their published values over `declared_ticks`, both
printed; the count of sections whose ledger `evaluated_frames` differs from
`producer_evaluated_ticks` is reported as the number of sections whose `evaluated_frames` should be
restated, with the signed difference distribution. A PROPOSED additive sidecar field
`evaluated_tick_ids` (list) for the producer is written to `PROPOSED_evaluated_tick_ids.md` in the
evidence directory as a proposal only; no `src/` file is edited.
