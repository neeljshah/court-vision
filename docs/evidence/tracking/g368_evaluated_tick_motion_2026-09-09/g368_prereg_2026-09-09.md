## 0. Scope, sign convention, and what this row is not

This row audits the PRODUCER's own writing behaviour: how often a written row
carries a position that a fresh detection drove, and how often it repeats the
previous one. It is a schema and calibration measurement of a tracking table. It
is NOT a court-geometry claim, NOT a tracking-quality verdict, NOT a downstream
forecast claim, and it carries no monetary or wagering interpretation of any
kind. No gate is re-barred here and no threshold is moved.

Sign convention. MOTION SHARE: higher means the producer moves positions more
often; the premise of this row is that it is LOW, so a HIGH value falsifies the
row (section 3). HELD-RUN LENGTH and HELD-TICK SHARE: higher means more repeated
positions, which is worse for a teacher corpus. ATTRIBUTED SHARE: higher is
better, bar in section 6. A displayed delta is ALWAYS the later state minus the
earlier state, and each table names its own two states in its header row.

## 2. The evaluated-tick marker rule (sealed)

MARKER = THE TABLE'S OWN `frame` FIELD. `tracking_data.csv` carries `frame` as its
first column (`src/pipeline/unified_pipeline.py:3978` lists it first in
`_tracking_csv_fields`, and it is written from `frame_idx` at
`src/pipeline/unified_pipeline.py:2706`). The header is byte-identical across the
inspected fresh and G358 sections (header SHA-256 prefix `2b6684361f72d3bc` on
`0SQ709_N0Yg_s1325`, `0SQ709_N0Yg_s2560`, `0SQ709_N0Yg_s3795` and
`1zPhldjbJnU_s1196`). The spec's fall-back ("else the ledger `evaluated_frames` /
stride") therefore does NOT apply: the table carries its own marker and the
ledger denominator is not used for the motion share.

WHY THE TABLE'S OWN MARKER AND NOT THE LEDGER. Two independent counts of
"evaluated frames" disagree on the same section, so a ledger-derived marker would
put an unexplained factor into the headline. On `0SQ709_N0Yg_s1325` the ledger
records `evaluated_frames = 1299` (`ticks.csv` line 2 of the G366 evidence, and
`decoded_frames 7793 / stride 6`), while the section's own sidecar
`evaluated_frame_count.json` records `evaluated_frames = 500` with
`max_frames = 3000` and the formula `ceil(decoded_frames / stride)`. A decode
capped at 3000 frames yields 500 ticks, not 1299. This row does not adjudicate
that disagreement -- it is recorded here as the reason the marker is taken from
the table -- and the finisher REPORTS both denominators beside the headline in
`motion.csv` (`ledger_evaluated_frames`, `sidecar_evaluated_frames`) without
dividing by either. Adjudicating the two counts is a SEPARATE gap; the memo
names it and does not resolve it.

EVALUATED TICKS OF A SECTION = the ascending, de-duplicated numeric values of
`frame` present in that section's `tracking_data.csv`. A row whose `frame` does
not parse as a number is dropped and counted in `motion.csv` as
`unparsed_frame_rows`. TICK PRESENCE is reported, never folded into the headline:
`motion.csv` carries `ticks`, `ledger_evaluated_frames` and
`sidecar_evaluated_frames` side by side so that a reader can see how many ticks
the producer never wrote a row on at all. The motion share's denominator is the
table's own tick pairs, so it cannot be inflated by a tick the producer skipped
(that is a coverage question, not a motion question, and mixing them would be B1).

## 3. Motion share, and the PREMISE FALSE condition (sealed)

For a section, order the evaluated ticks ascending. For each CONSECUTIVE PAIR of
evaluated ticks (t_prev, t_cur), let S be the set of `player_id` values present at
BOTH t_prev and t_cur. The pair COUNTS AS MOVED when at least one member of S has
a `(x_position, y_position)` string pair at t_cur that is not byte-identical to
its pair at t_prev. A track present at only one of the two ticks contributes
nothing to that pair -- it can neither move nor be held -- and a pair with S empty
is NOT MOVED and stays in the denominator.

    motion_share = moved_pairs / (number of evaluated ticks - 1)

Comparison is on the DECIMAL STRINGS as written by the producer, never on parsed
floats, so that "byte-identical" means what the file says (this is the same
convention the landed G359 rule uses at
`scripts/platformkit/tracking/g359_held_position.py:70-72`).

PREMISE FALSE CONDITION (binding, checked before anything else is reported): if
the MEDIAN of `motion_share` over CORPUS 1 is >= 0.90, the premise of this row is
FALSE. The finisher then STOPS, writes the memo with `VERDICT: PREMISE FALSE`,
states in the memo that G366's evaluated-tick ratio (median 0.153195) is in that
case a COLLAPSE-RULE artifact rather than evidence of held positions, commits,
and reports. No attribution, consequence or proposal is produced on that branch.
The premise is judged on CORPUS 1 alone; CORPUS 2 is reported beside it and
cannot flip the verdict.

## 4. Held runs and the census fields (sealed)

Sort each section's rows by `player_id`, then by numeric `frame`, stable. A HELD
STEP is a row whose `(x_position, y_position)` string pair is byte-identical to
the PREVIOUS ROW OF THE SAME TRACK. A RUN is a maximal chain of consecutive rows
of one track that are pairwise held; its LENGTH is the number of rows in the
chain, so a run of length L contains L-1 held steps and a track row that repeats
nothing is a run of length 1. A HELD RUN is a run of length >= 2. Adjacency is in
the track's OWN row order, not in the global tick list, which is exactly the
landed G359 convention -- a track that misses a tick and returns with the same
position is still one run, and the memo says so.

`held_runs.csv`, one row per section per corpus:
`section_name`, `corpus`, `rows`, `ticks`, `tracks`, `runs_n`, `held_runs_n`,
`held_steps_n`, `run_len_p50`, `run_len_p90`, `run_len_max` (all three over HELD
RUNS only, and empty when `held_runs_n` is 0), `tick_share_in_runs_ge2`,
`tick_share_in_runs_ge5`, `tick_share_in_runs_ge30`. Each `tick_share_in_runs_geK`
is the number of ROWS lying in runs of length >= K divided by the section's total
player rows; the denominator is named in the header comment of the file and in the
memo (H1). Percentiles are `statistics.quantiles`-free: `run_len_p50` and
`run_len_p90` are the nearest-rank order statistics of the sorted held-run
lengths at ceil(0.50 n) and ceil(0.90 n), so they are integers and reproducible
without a library version dependency.

## 5. PRODUCER BRANCH LIST -- every path that can emit a row without a fresh detection-driven position

Read from `src/` in this worktree at master 4a272c50, before the seal. `src/` is
READ and IMPORT only in this row; nothing below is edited.

P1 TRACKER VELOCITY CLAMP -- `src/tracking/advanced_tracker.py:632-640`. A
   matched detection exists, but its projected 2D position jumps more than
   `MAX_2D_JUMP * stride` from the track's last known position, so
   `new_pos = last_pos` (`:636`) and `self._freeze_age[slot]` is incremented
   (`:637`) before `p.positions[timestamp] = new_pos` (`:640`). Emits a
   BYTE-IDENTICAL position while a detection was present.

P2 KALMAN COAST -- `src/tracking/advanced_tracker.py:1638-1655`. A track with no
   match this tick but an active Kalman prediction (`self._kf_pred[slot]`, set at
   `:1162`) has the predicted box projected and written as
   `p.positions[timestamp] = (homo[0], homo[1])` (`:1654`). NO detection drove
   this position. Consecutive predictions from a near-zero-velocity state project
   to the same integer, giving a held run.

P3 OPTICAL-FLOW GAP FILL (batched, populated frame) --
   `src/tracking/advanced_tracker.py:1658-1701`. Lost tracks with
   `0 < _lost_ages <= OF_MAX_AGE` are propagated by Lucas-Kanade and written at
   `:1698`. NO detection drove this position.

P4 OPTICAL-FLOW GAP FILL (empty frame / YOLO blackout) --
   `src/tracking/advanced_tracker.py:1270-1318`, written at `:1311`, reached from
   the `len(boxes_xyxy) == 0` branch after `self._age_all(timestamp)`. Same
   mechanism as P3 on a frame with zero detections.

P5 PIPELINE JUMP CLAMP -- `src/pipeline/unified_pipeline.py:2026-2033`. A SECOND
   clamp, downstream of P1, in the row builder: when the position moved more than
   350 px from `prev_pos`, `x2d, y2d = last_pos[0], last_pos[1]` (`:2033`). Emits
   a byte-identical position with a fresh detection present.

P6 INTEGER QUANTISATION -- `src/pipeline/unified_pipeline.py:2042-2043`. The row
   builder stores `int(x2d)` and `int(y2d)`, so any true motion below one unit is
   written as a byte-identical position. Not a hold in the producer's state, but
   a genuine source of held runs in the TABLE, which is what this row measures.

P7 BALL-TABLE CARRY-OVER -- `src/pipeline/unified_pipeline.py:1977` takes
   `ball_pos = self._last_ball_2d`, a value that persists across frames, and the
   ball row is written from it at `:1991-2003`. This branch IS FLAGGED in the
   table: `detected` (`:2000`) and `ball_inferred` (`:2002`, the G320 flag).

P8 BALL POSSESSOR FALLBACK -- `src/pipeline/unified_pipeline.py:1985-1988`. When
   the ball is lost, the possessor's own 2D position is used as the ball position
   (`:1987`); the row is then written with `detected = 1`, so this branch is NOT
   distinguishable from a real ball detection in the ball table.

Branches that SUPPRESS a row rather than hold one -- listed because they shape the
tick-presence numbers and must not be mistaken for holds:
S1 `src/pipeline/unified_pipeline.py:2022-2023` -- a track with no entry in
   `p.positions` for this tick emits NO ROW at all (this is why an absent
   detection does not by itself create a held row).
S2 `src/pipeline/unified_pipeline.py:2703-2704` -- a bounding box with no overlap
   with the decoded frame is dropped (the G325 rule).
S3 `src/pipeline/unified_pipeline.py:2657-2661` -- at most 12 non-referee tracks
   per tick, sorted by `confidence` descending.
S4 `src/tracking/advanced_tracker.py:1720-1734` -- same-team duplicate
   suppression deletes `positions[timestamp]` for one of two colliding tracks.

## 6. Attribution rule (sealed): table fields -> branch classes

FIELDS THE PLAYER TABLE ACTUALLY CARRIES. Inspected on
`/workspace/data/tracking/0SQ709_N0Yg_s1325/tracking_data.csv` (1366 rows) and
`/workspace/data/tracking/1zPhldjbJnU_s1196/tracking_data.csv` (4017 rows):
`frame`, `timestamp`, `player_id`, `team`, `x_position`, `y_position`, `x_norm`,
`y_norm`, `velocity`, `acceleration`, `direction_deg`, `confidence`,
`bbox_x1`..`bbox_y2`, `homography_valid`, `coordinate_space`, `observation`,
`calibration`, and 50 further enrichment columns. THERE IS NO `inferred` COLUMN,
NO `coast` COLUMN AND NO `status` COLUMN ON THE PLAYER TABLE. `observation` is a
schema CONSTANT (`observed` on 1366 of 1366 rows of the inspected section; the
adapter stamps the constant at `domains/basketball/tracking/adapter.py:118`) and
so are `coordinate_space` (`image_px`), `calibration` (`none`) and
`homography_valid` (`1`) on that section -- none of them can attribute anything,
and using a constant as a discriminator would be B9. The `inferred` flag exists
ONLY on the BALL table, whose header is
`frame,timestamp,ball_x2d,ball_y2d,detected,live,ball_inferred,ball_x2d_px,ball_y2d_px`.

THE DISCRIMINATOR IS `confidence`. `src/pipeline/unified_pipeline.py:2036` sets
`conf = max(0.0, 1.0 - self.feet_det._lost_ages.get(slot, 0) / 15)`, so
`confidence == 1.0` if and only if the slot's `_lost_ages` is 0, i.e. the slot was
MATCHED TO A DETECTION on this tick; `confidence < 1.0` means `_lost_ages > 0`,
i.e. the position came from P2, P3 or P4 and NO detection drove it. The implied
lost age is `round((1 - confidence) * 15)`. The field is fully populated and
strongly varying on both inspected sections (`1.0` on 1022 of 1366 and on 1527 of
4017 rows respectively; 0 blanks in both), so it is neither constant nor sparse.

SEALED CLASSES, evaluated per HELD STEP, FIRST MATCH WINS, in this order:

C1 UNATTRIBUTED -- `confidence` is blank or does not parse as a number, or the
   previous row of the track carries no bounding box fields. This is the
   FALL-THROUGH: absent evidence lands here and is never reclassified as
   something else (B3).
C2 COAST_LOST -- `confidence` parses and is strictly less than 1.0. Branches P2,
   P3, P4. The row was emitted with no detection on that tick.
C3 BBOX_FROZEN -- `confidence` equals 1.0 AND all four `bbox_*` values are
   byte-identical to the previous row of the same track. `p.previous_bb` is
   assigned only inside `update_position`
   (`src/tracking/advanced_tracker.py:626`), so an unchanged box alongside a
   zero lost age means the box was not refreshed on this tick.
C4 CLAMP_OR_SUBPIXEL -- `confidence` equals 1.0 AND at least one `bbox_*` value
   differs from the previous row. A detection drove this tick and the position
   was still written byte-identical, which is P1, P5 or P6.

HONEST LIMIT OF THE RULE, stated before any number: C4 CANNOT BE SPLIT further by
the fields the table carries. P1 (tracker clamp), P5 (pipeline clamp) and P6
(integer quantisation) are indistinguishable in `tracking_data.csv`, and a
genuinely stationary player also lands in C4. The memo MUST state this and MUST
NOT report C4 as "clamping". This inseparability is the whole motivation for the
section-9 proposal.

RUN CLASS. A HELD RUN's class is the class holding the MAJORITY of its held
steps; a tie is broken by the sealed order C1 < C2 < C3 < C4 above, taking the
FIRST listed class among those tied.

BAR (byte-identical to the spec, never moved): ATTRIBUTED SHARE = held steps in
C2, C3 or C4 divided by ALL held steps, over CORPUS 1, must be >= 0.95. Note
plainly in the memo that this bar measures COVERAGE of the rule, not resolution:
under C1's narrow definition nearly every held step attributes, and the
INFORMATIVE numbers are the per-class SHARES, which the memo quotes first.

`attribution.csv`, one row per section per class: `section_name`, `corpus`,
`class`, `held_steps`, `held_step_share`, `runs`, `run_share`, plus the
section-level `coast_row_share` (section 8) repeated for readability.

## 7. Controls (sealed, exact)

K1 ALL-MOVING SYNTHETIC. 60 evaluated ticks at stride 6, 5 tracks, every track's
   `x_position` and `y_position` advanced by a non-zero integer at every tick,
   `confidence` 1.0 everywhere, bounding boxes advanced with the position.
   REQUIRED, EXACTLY: `motion_share == 1.000000`, `held_runs_n == 0`,
   `held_steps_n == 0`. Any other value fails the run.

K2 PLANTED COAST. The same table with ONE track frozen for 30 CONSECUTIVE ticks:
   its `(x_position, y_position)` and all four `bbox_*` values are repeated
   unchanged, and its `confidence` is stepped DOWN the real ladder
   `1 - k/15` (k = 1..15, then held at the floor) so that every planted row
   carries `confidence < 1.0`. REQUIRED, EXACTLY: exactly one held run of length
   30, `held_steps_n == 29`, and `COAST_LOST` attribution share `== 1.000000` over
   the planted held steps, with `UNATTRIBUTED == 0`.
   WHY THE PLANT USES `confidence` AND NOT AN `inferred` COLUMN: the player table
   has no `inferred` column (section 6); planting one would test a schema the
   producer does not write, which would be a control that cannot fail. The ball
   table's real `ball_inferred` flag is exercised separately in K2's companion
   ball table, where a 30-tick carry-over is planted with `detected = 1` and
   `ball_inferred = 1` and must attribute to P7 with share 1.000000.

K3 SECOND SNAPSHOT. CORPUS 2 (the 34 G358 sealed sections) is reported with the
   same `motion.csv`, `held_runs.csv`, `attribution.csv` and `consequence.csv`
   rows, marked `corpus=G358`. NO BAR is applied to it and it cannot change any
   verdict; it exists so that no headline rests on a single corpus (Q5).

`controls.csv` records, per control, the required value, the observed value and a
PASS / FAIL flag. A FAILING control STOPS the run before any corpus is scored.

## 8. Consequence table (sealed)

The M1 rule is IMPORTED, never restated: `collapse_held` from
`scripts/platformkit/tracking/g359_held_position.py:111-122`, fed a frame with
`cls = "player"`, `track_id = player_id`, `x = x_position`, `y = y_position`,
`frame = ` the numeric tick. Per HELD RUN the outcome is MEASURED, not assumed:

    KEPT          -- M1 removes no row of the run
    REMOVED_TAIL  -- M1 removes exactly rows 2..L and keeps row 1
    SPLIT         -- anything else (M1 removes a row and keeps a later one)

`consequence.csv`, one row per section per corpus: `section_name`, `corpus`,
per-class counts of KEPT / REMOVED_TAIL / SPLIT, `m1_rows_dropped` (the count
`collapse_held` itself returns), `motion_share` (section 3),
`motion_share_no_coast`, and `coast_row_share`.

`coast_row_share` = player rows with `confidence < 1.0` divided by ALL player
rows of the section. This counts every row emitted with no detection behind it,
whether or not its position happened to repeat -- a Kalman coast that MOVES is
still a coast, and restricting the count to held rows would understate it.

`motion_share_no_coast` = the section-3 motion share recomputed after DELETING
every player row with `confidence < 1.0`, ticks re-derived from the surviving
rows. This is the number the teacher admission filter needs: the share of ticks
that still show motion once rows no detection drove are gone. It is reported as
a calibration diagnostic and never as a quality verdict.

## 10. Eye check -- 10 strips, evenly spaced, never a head slice

Ten strips over CORPUS 1. Sections are ordered by `section_name` ascending and
the strip indices are `floor(i * n / 10)` for i in 0..9, so the sample spans the
whole ordered set (A3; a head slice is how G11 v1 reported 0.93 for an honest
0.78). Within a chosen section the rendered track is the `player_id` with the
most rows, ties broken by the smallest `player_id` string, so the choice is
deterministic and recorded in `strips/manifest.csv` alongside the section name and
the track id. Each strip is a standalone SVG drawing `x_position` and
`y_position` against the evaluated tick as two polylines, with every held run of
length >= 2 shaded as a band behind them. SVG is written by hand, with no
plotting library, so the render is byte-reproducible from the CSV. TOTAL size of
`strips/` must be <= 200 KB; the writer refuses and prints the total when it is
not, and the memo quotes the observed total.
