# G194: Which M1 does the WNBA pipeline use?

## Result

All three instrumented pod runs used the `Rectify1.npy` fallback as their
initial and final projection M1.  Each run made five recovery fresh-solve
attempts; every attempt returned `None`.  No run ever set `_M1_raw_clip`.

The final M1 was elementwise identical to the pod's `Rectify1.npy` in all
three runs (`np.array_equal == True`, maximum absolute element delta `0.0`).
Thus, for this bounded 1,200-source-frame route, the M1 actually used for
projection was the static resource, not a recovered per-clip matrix.

This answers the branch question only. It does not establish whether the
static resource is geometrically valid or invalid for this footage.

## Scope and method

The measurement ran on the pod at `/workspace/nba-ai-system` (RTX 3090,
24,576 MiB). The source clip was verified before the runs as
`data/footage_corpus/wnba__wnba_01.mp4`, 2,931,985,407 bytes, 1920x1080, and
174,430 frames.

The standalone read-only harness was copied to
`/workspace/g194_a6_20260903/g194_m1_pipeline_measure.py`, outside the pod
checkout. It temporarily wrapped `_build_court`, the `unified_pipeline`
detector call binding, `court_detector.detect_court_homography`, recovery,
and `_get_homography` in its own process. The wrappers only observed inputs,
returned values, and M1 state. The pod checkout, daemon, keeper, source clip,
and production code were not changed.

Each run invoked the unchanged route arguments through that wrapper:

```text
python3 .../g194_m1_pipeline_measure.py --project /workspace/nba-ai-system \
  --output-dir /workspace/g194_a6_20260903/runN_measure -- \
  --video data/footage_corpus/wnba__wnba_01.mp4 --frames 1200 --no-show \
  --skip-features --data-dir /workspace/g194_a6_20260903/runN_data
```

The raw per-invocation records are committed rather than reduced to this
table: [run 1 JSON](g194_which_M1_2026-09-03/run1_measure/g194_m1_measurement.json),
[run 2 JSON](g194_which_M1_2026-09-03/run2_measure/g194_m1_measurement.json),

visible red boundary line crosses the lower-left crowd/broadcast-overlay area
rather than a painted court line. This is an eye-check observation of these
two projected samples, not a calibrated geometric-error metric.

## Orchestrator verification and eye check at landing

**A1:** `test_g194_m1_pipeline_measure.py` 1 passed in master.

**Branch result confirmed from the committed JSON:** 3 of 3 runs took the
`Rectify1.npy_fallback` branch, made 5 fresh-solve attempts each, succeeded 0
times, never set `_M1_raw_clip`, and ended with an M1 elementwise identical to the
static resource (max delta 0.0).

### `run_clip.py:581` is WRONG, and it misled this programme

That comment states a per-clip homography "is solved in memory and discarded".
**Nothing is solved.** The solver is called and returns `None` every time; the
static file is what the pipeline projects with. The comment sent both the Fable
review and me toward "basketball's failure is plumbing -- just persist the matrix
it already has", and there is no such matrix. **The comment should be corrected in
a human-gated edit; it is actively misleading as written.**

### The eye check the spec required, done by the orchestrator

I viewed `run1_measure/court_projection_400_of_400.jpg` directly. The render's own
metadata confirms it draws the court model through this M1.

**The projected court is a single red diagonal line running from the upper-left,
across the crowd, and off the bottom of the frame.** The painted WNBA court is
plainly visible in the same image -- baselines, three-point arc, paint, centre
circle -- and the projection bears no relationship to any of it.

**This is a DEGENERATE projection, not an inaccurate one.** The court model
collapses to a line. That is a categorically different failure from "the
calibration is off by N pixels", and it is exactly what `unified_pipeline.py:885-887`
predicts: that matrix is calibrated for the `pano_enhanced` panorama at 3698x500
and "a per-video broadcast frame would break M1". The warning in the code was
correct and has been firing silently on every basketball clip.

**It also explains a symptom two other rows flagged and neither could own.** G189
and G193 both reported survivor coordinates far outside the frame (x = 2979,
y = -1699 on a 1920x1020 crop). A degenerate projection maps the image onto a
line, so points land at absurd magnitudes. That is the mechanism.

### What this means for basketball, stated carefully

**Basketball has never had a working court projection in this route.** Not a poor
one -- an unusable one. Every `court_feet` figure this route could have produced
for basketball would have been meaningless, which makes the affine-rescale
persistence at `run_clip.py:581` look less like a shortcut and more like something
substituted because the real projection was unusable.

**NOT claimed:** that basketball cannot be calibrated. G136 measured four-corner
geometry visible in 46.2 pct of basketball frames. This says the CURRENT static
fallback is degenerate on this footage, on one clip, over three runs of one
bounded route. Whether a per-clip solve is achievable is the open question, and
G192b already showed the existing Hough solver returns nothing on 17 of 17
corner-visible frames.
