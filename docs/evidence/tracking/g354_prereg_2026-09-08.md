# G354 Preregistration - Ball Pixel Producer Fields (2026-09-08)

Written before any G354 smoke, deploy, post-deploy range check, or radius re-join.
Contract: `docs/evidence/tracking/VERIFIER_CONTRACT.md`, sections A and B; Q1 is
satisfied by this sealed file before any comparison. No OOS model score is planned.

## Field contract

The producer adds `ball_x2d_px` and `ball_y2d_px` after the existing ball fields.
Each is the integer `(x, y)` centre of the current dedicated detector/tracker bbox or
the current alternate YOLO ball bbox, in the TOPCUT-cropped pixel frame used by
`bbox_x1..bbox_y2`. Existing field names, order, values, and semantics remain unchanged.
A frame with no current bbox writes the explicit empty string for both new fields; it
must never reuse a prior-frame value. A valid coordinate component of zero is written
as `0`, not as an empty string. The old court-map fields remain unchanged.

## Fixed checks and decision rules

The local smoke is one headless 130-second section. It requires both new fields and
per-axis ball-pixel p01/p99 range divided by the matching player bbox range no greater
than 1.5. The post-deploy check requires at least three ledger entries dated after the
recorded UTC deploy timestamp; each fresh clip must have both fields and meet the same
per-axis ratio rule. Pre-deploy clips never count. The fixed re-join is a 60-pixel
point-to-player-rectangle radius count with the pixel fields and with old fields, both
reporting their finite/detected frame denominator. Improvement sign convention for any
delta: baseline loss minus candidate loss; positive means candidate better. Here the
re-join counts are diagnostic, not a loss or calibration claim.

## Deployment recipe

After tests and local smoke pass, the finisher LF-normalizes only the patched producer
files, copies them by scp to a pod scratch path, records SHA-256 before and after, and
atomically moves them into `/workspace/nba-ai-system/`. The finisher records UTC time
and `git -C /workspace/nba-ai-system status --short` for those files. No daemon or
guard restart, flag change, data write, registry write, or ledger write is permitted.
The post-deploy checker reads one clip store at a time and writes its CSV outputs outside
`data/`.
