### (a) S124 -- `assert_tick_asof` now also asserts LABEL BLINDNESS

`assert_label_blind(src, builder, labels=None)` rebuilds the table with every label column
PERMUTED and requires every feature column to be unchanged **over all rows**, not a probe
sample (a probe sample can coincide on a binary label; the full comparison cannot). The
permutation is a seeded shuffle retried over up to 8 fixed seeds until the values actually
differ -- a fixed roll is value-identical on a periodic label, which is a real case and was
caught by the test. Label columns are the frozen set
`("outcome", "y", "label", "settled", "result", "won")`, plus an explicit `labels=` sequence a
caller can pass when the label lives outside `src`.

`assert_tick_asof` calls it after the truncation loop, so the two guards are one call.

```
assert_tick_asof on the SAME same-tick-label builder, after the fix:
  TickTimeLeak: label_now changed on 836 of 1680 rows when the label columns ['y']
                were permuted: it reads its own tick's label
```

**Default: ON, and it is a no-op on every landed archive.** The production path builds `src`
from `causal_source`, whose frame carries `game / timestamp / state_summary / _row_id` and no
label at all, so `assert_label_blind` returns the EMPTY list, performs no extra build and
changes nothing. That is also its limitation, stated plainly: **on the S82/S102/S114 corpora
as wired today the guard checks nothing**, because the label is not reachable from `src`. It
binds only when a caller passes `labels=`, or when a corpus carries the label in `src`.

**KNOWN GAP, NOT FIXED HERE.** The S124 row also asks for a second gate inside `run()` /
`sweep()` refusing a candidate column whose per-game variance is zero and whose per-game value
tracks the label, plus an assertion that every served column name is a frozen-grammar member.
`run(features=...)` still accepts an arbitrary mapping and is NOT gated. That half of the row
stays OPEN.

### (d) S131 -- a boundary needs corroboration, and `_ts` parses epoch seconds

`_boundary` now evaluates the > `gap_hours` rule first, then requires an inning decrease to be
CORROBORATED by either at least `min_gap_minutes` (default **20.0**, `DEFAULT_MIN_GAP_MINUTES`)
since the previous in-play tick, or a simultaneous score reset; a standalone score reset needs
the same time floor. An unparseable stamp leaves the gap UNKNOWN and an unknown gap does not
veto (contract B3, missing is not bad), so a store with no usable clock behaves as before.
`_ts` parses epoch seconds (and milliseconds past 1973) as a third format, and
`assign_real_game_seq` RAISES when no value in the ts column parses at all.

**Default: changed, not opt-in.** The corrected split is what S106/S119/S121 must be quoted
against; keeping the old rule as the default would keep every MLB in-game interval 4.2 pct too
narrow. `min_gap_minutes` is a keyword argument, so the old behaviour is reachable with
`min_gap_minutes=0.0` for an A2 reproduction.

```
after the fix, the same live store:
  n_game_ids 227  n_real_games 360  n_multi 112  n_ticks_reassigned 21,318
  boundary_reasons {"ts_gap": 129, "inning_decrease": 4}
  boundaries fired: 133 ; whose previous in-play tick is < 10 min earlier: 0
  genuine (> 5 h) splits surviving: 129
  _ts("1751328000") -> 2025-07-01 00:00:00 ; _ts(1751328000.0) -> 2025-07-01 00:00:00
```

**Store-wide: 392 -> 360 real games**, exactly the memo's predicted ~360. All 32 near-instant
boundaries are gone and all 129 genuine long-gap splits survive. `boundary_reasons` shifts
because `ts_gap` is now evaluated FIRST: a > 5 h split that also carried an inning decrease used
to be labelled `inning_decrease` and is now labelled `ts_gap`. Total boundaries 165 -> 133,
