## The four open prior-red-team items, re-checked on disk today

All four were still open. Three were <=20 LOC additive and are fixed; one is not.

- **agent 1.1 -- FIXED.** `_verdict` returned `BEATS_CLOSE` on the RAW `dm.p_value` while
  `corrected_dm_p` / `ship_eligible` were written later and never consulted. A
  `BEATS_CLOSE` the corrected p does not support is now downgraded to `MATCHES_CLOSE`
  with the raw label preserved in `verdict_uncorrected`. While there: `_verdict`'s
  fallthrough labelled a strictly POSITIVE interval "BEHIND", contradicting its own
  documented contract; `BEHIND` now requires a strictly negative interval, so an
  uncleared positive interval reads as the non-claim `MATCHES_CLOSE`.
- **agent 1.3 -- FIXED.** `DM_MIN_N = 200` was tested against `dm.n` (raw STATES) while
  the SE producing the p-value clusters by game; the golden fixture is 103 states over
  70 `game_id`s. The floor now binds `dm.n_clusters` as well as `dm.n`.
- **agent 1.2 -- FIXED.** `load_golden` ran only the structural `validate_golden`, so a
  schema-valid hand edit silently redefined "gate green". `GOLDEN_SHA256 =
  fe9298fc5aef80b10a799d547057374b291c4bb465fb1cf3e3aae2ed03cbcbf2` seals the DEFAULT
  fixture's bytes and fails closed on any change; a caller-supplied path is deliberately
  unsealed (tests and alternative corpora are unaffected). Regenerating the fixture with
  `gen_golden` is expected to break this on purpose -- the new digest must land in the
  same commit as the new fixture.
- **agent 3 -- PROPOSED, not fixed.** `run_gate.py` still sets `n_trials = len(CORPORA)`
  = 2 rather than the cumulative ledger K. Fixing it means reading
  `data/cache/eval_gate/backtest_fwer.jsonl` from inside `run_gate`, which breaks
  `--golden`'s stated offline / no-`data/` contract. It needs its own register row: a
  caller-supplied `n_trials` (defaulting to the current value) that the charged callers
  pass their launch K into, leaving `--golden` unchanged.

## Design note on RT-18's default

`redact_test_view(state, *, allow_keys=(), strict=False)` is the single redaction both
harnesses now use (`cpcv_engine` IMPORTS it instead of hand-copying the key tuple, so the
two can no longer drift). `strict=False` reproduces the pre-S40b deny-list byte for byte,
because a fixed allow-list is NOT safe as a silent default: `edge_engine/score.py:169`
reads `test.get("signal_value")` and `student_gate` reads `test.get(id_key)` off the test
view, so dropping undeclared keys by default would have changed those predictors' outputs
without an error. Strict mode is therefore opt-in, and `run_gate` -- the fail-closed path,
whose only corpus is the golden fixture -- opts in. A caller that genuinely needs a key on
the test row declares it in `allow_keys`; anything neither declared nor a known settled
name raises.
