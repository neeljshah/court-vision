# S665 -- cdn.nba.com block mechanism, laptop egress (2026-09-30)

VERDICT: OPEN (the literal rule would read IP; downgraded because HTTP/2 is untested and IP vs fingerprint is
not separable). Laptop, HTTP/1.1 only. All three arms returned HTTP 403 with the same CDN "Access Denied"
page. A browser-like header set over HTTP/1.1 does NOT clear the block. The HTTP/2 arm could not run from this
laptop (see below), so the register's HEADER-vs-IP question stays open. The block is an explicit 403 response,
not a silent drop or timeout, at the moment of the probe. The literal spec rule gives IP (laptop, HTTP/1.1),
because all three arms failed identically. The verdict is downgraded to OPEN because arm 3 did not exercise HTTP/2
as the spec intended.

What this decides and what it does not:
- Header-only mechanism over HTTP/1.1: RULED OUT on this egress. The five-header browser set gives the
  same 403 as a bare client.
- Silent datacenter-style drop: NOT what the laptop sees. The CDN answers promptly with a 403 page.
- HTTP/2 plus headers (the variant memo F section 1c reports as working): NOT TESTED. The installed curl
  (Schannel build) negotiated HTTP/1.1, and the python `h2` package is not installed, so httpx cannot speak
  HTTP/2. Installing a package was out of scope for this read-only lane.
- IP reputation versus TLS/HTTP fingerprint: NOT separable from these three arms. Both fit an identical 403
  on every arm.
- 60-minute window and VM egress (register acceptance): NOT RUN. This is a single laptop snapshot.
