## (a) `--k-source {corpora,ledger}`

`resolve_n_trials(k_source, ledger_path, allow_noncanonical_ledger)` in
`scripts/platformkit/eval_gate/run_gate.py`:

- `corpora` (DEFAULT) returns `len(CORPORA)` -- today's behaviour byte for byte. It
  imports nothing new and opens no file under `data/`, so `--golden`'s offline contract
  is untouched.
- `ledger` returns `max(k_cumulative)` over the canonical FWER ledger, READ-ONLY. The
  ledger modules (`backtest_runner`, `ledger`) are imported INSIDE this branch so the
  `--golden` path never pulls the ledger/pandas stack in.
- The S40b/RT-3 rule is reused verbatim: `assert_canonical_ledger` raises
  `refusing to charge a trial against a non-canonical ledger` before anything is read,
  unless the caller passes `allow_noncanonical_ledger=True` (tests only). A fresh path
  restarts K and would LOOSEN the per-test bar; that is exactly what is refused.
- `run_gate` appends NOTHING. It is not a charged trial -- it reads the K a charged
  caller already established. `_charge_ledger` is not imported here.
- Every scoreboard row carries `k_source` beside the existing `n_trials_this_sweep`
  (additive; no existing key renamed or removed -- B2). The scoreboard's `K` column
  already prints the K; the SOURCE line is printed only when `k_source != "corpora"`,
  which is what keeps the default sweep's stdout byte-identical (below).
- CLI: `--k-source {corpora,ledger}`, default `corpora`. `--golden` REFUSES anything
  else: `--golden runs offline and accepts --k-source corpora only` (argparse exit 2).
  Measured: `python -m scripts.platformkit.eval_gate.run_gate --golden --k-source ledger`
  -> that error, exit 2.

## (b) golden digest sidecar

- `gen_golden.write_sidecar(out)` writes `<fixture>.sha256`; `gen_golden.emit_seal(out)`
  calls it and then refreshes the `GOLDEN_SHA256 = "..."` line in `golden_loader.py` in
  place, so a legitimate regeneration needs no hand-computed and no hand-edited constant.
  `main()` calls `emit_seal` after writing the fixture and prints the digest.
- `golden_loader.expected_seal(p)` returns `(digest, source)`: the sidecar when present,
  the constant otherwise. When BOTH exist they must agree -- a disagreement raises
  `golden seal disagreement` naming the sidecar value AND the constant value. `load_golden`
  then compares the fixture's bytes to that expectation and raises
  `golden fixture seal mismatch` naming `expected` (with its source) and `got`.
  A caller-supplied path stays deliberately unsealed, exactly as under S40b.
- Regeneration run for real: `python scripts/platformkit/eval_gate/gen_golden.py` ->
  `OK 103 states`, `GOLDEN_SHA256 = fe9298fc5aef80b10a799d547057374b291c4bb465fb1cf3e3aae2ed03cbcbf2`.
  `git status` after: the fixture is UNMODIFIED (the builder is deterministic, so the
  regenerated bytes are the committed bytes), the sidecar is new, and the rewritten
  constant is the same 64 hex characters that were already there. Sidecar and constant
  therefore agree on the committed fixture, and the sidecar is committed with it.
