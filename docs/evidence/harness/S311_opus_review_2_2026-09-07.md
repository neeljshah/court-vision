## Verdicts

### patched2/codex_pipeline.sh and patched2/codex_pipeline_g.sh -- ACCEPT WITH CORRECTIONS (R1)

**R1 (BLOCKING).** The sha is derived from `git -C nba-track-$home log master..HEAD` on EVERY tick,
BEFORE the verify log is consulted (`patched2/codex_pipeline.sh:83`, `codex_pipeline_g.sh:81`). The
live loop only does that inside `[ ! -f "$vlog" ]` (`bin_copy/codex_pipeline.sh.live_2026-09-07:26-27`).
Two consequences, both measured today:

1. A landed row's worktree has nothing ahead of master, so the empty sha falls into the new
   NO COMMIT branch and spawns `python lane_commit.py <home> <SID>` every 30 s, forever. Right now
   S304 (a18) and S306 (a16) are exactly that shape -- verified, landed, `master..HEAD` empty --
   so the installed file would start two python processes per tick and could commit stray files
   in already-landed worktrees with no orchestrator involved.
2. Worktree homes are recycled across rows. Once a18 is handed to a later row, `cx_s304.log`
   (which never leaves Temp) would resolve S304's sha to that row's commit and re-verify S304
   against it.

The same ordering also loses READY TO LAND for any ACCEPTed row whose commit already merged
(loop-matrix case 2 fails on patched2, passes on patched2_fixed).

Corrected lines (applied in `patched2_fixed/codex_pipeline.sh:83-90`, same shape at
`codex_pipeline_g.sh:81-88`; generated by `tests/apply_r1.py`) -- move the vlog/llog definitions
above the sha lookup and replace `sha=$(git ...)` with:

    sha=
    [ -s "$vlog" ] && sha=$(awk '/^DISPATCHED verify=/{v=$0} END{ if (match(v,/sha=[0-9a-f]+/)) print substr(v,RSTART+4,RLENGTH-4) }' "$vlog")
    if [ -z "$sha" ]; then
      sha=$(git -C "/c/Users/neelj/nba-track-$home" log --format=%h -1 master..HEAD 2>/dev/null | awk '...')
      if [ -z "$sha" ]; then
        <the existing lane_commit block, unchanged>
      fi
    fi

`[ -s "$vlog" ]` (not `-f`) keeps the empty/placeholder-verify-log case falling through to a
dispatch, which the attempt-2 matrix asserts.

**R4 (BLOCKING, found by the live-log dry run).** The same recycled-home hazard exists in the
NO-COMMIT direction, and it is live right now: `cx_g293_footpoint_content.log` (EXIT:0, no
commit) names `wt=a7`, and a7 is TODAY running G304P1 (`cx_g304p1_locator_pass1.log`, appended
17:43). The first tick of patched2's G loop called `lane_commit.py a7 G293` -- i.e. it would
commit the running G304P1 lane's work-in-progress under a G293 message and then dispatch a G293
verifier against it. Applied in `patched2_fixed/codex_pipeline.sh:85-92` and
`codex_pipeline_g.sh:83-90`, immediately before the `git log master..HEAD` lookup, so it gates
both the sha read and the commit:

    own=$(ls -1t "$T"/cx_*.log 2>/dev/null | while read -r g; do
            case "$g" in *cx_verify_*|*cx_land_*) continue ;; esac
            gh=$(grep -a "^DISPATCHED" "$g" | tail -1 | sed -E 's/.*wt=(a[0-9]+).*/\1/')
            [ "$gh" = "$home" ] && { printf '%s\n' "$g"; break; }
          done)
    [ "$own" = "$f" ] || continue

Only the newest build log naming a home may read or commit it. After R4 the dry run's G tick
makes no lane_commit call at all, and both loops' first post-bounce ticks dispatch nothing.

Everything else in both files is accepted as
written: READY TO LAND + empty-land-log sentinel preserved verbatim, last-DISPATCHED EXIT scoping
preserved, lane_commit called in the NO COMMIT branch with `LANE_COMMIT <sha>` proceeding to
verification on the same tick, G dedupe fixed, POSIX sh throughout.

**R2 (BLOCKING for lanes).** `[ "$tar_rc" -eq 0 ]` (`patched2/pod_run:129`) makes tar's rc=1
fatal. rc=1 is "file changed as we read it", which the live launcher deliberately tolerated
(`bin_copy/pod_run:32`, comment "tar exit 1 = files changed while reading (ok)"), and lanes run
`pod_run` from INSIDE their own live worktree while codex is writing to it. Applied in
`patched2_fixed/pod_run:129-131`:

    # tar rc=1 is "file changed as we read it" ...

The `tar failure` fixture (rc=8) still exits 4, so nothing weakens.

**R3 (BLOCKING, found by the first real smoke test).** The ship manifest is produced by
`print(rel)` from an embedded python whose stdout is TEXT mode, so on Windows every manifest line
ends `\r`. `tar -T` then cannot stat a single path. The first `pod_run a22 -- python --version`
against the real pod died with hundreds of
`tar: tests/test_win_probability.py\r: Cannot stat: No such file or directory` and
`pod_run: ship tar failed rc=2`. The attempt-2 fixture cannot see this: its fake `tar` is a
python script that ignores `-T` entirely, so no real manifest was ever consumed. Applied at
`patched2_fixed/pod_run:110-111`:

    # stdout is text mode: print() emits CRLF on Windows and tar -T cannot stat those paths
    for rel in sorted(out): sys.stdout.buffer.write((rel + "\n").encode("utf-8"))

in `build_prompt.txt`, `codex-verify`, `codex-verify-g` and `codex-land` uses the `--` form, so
