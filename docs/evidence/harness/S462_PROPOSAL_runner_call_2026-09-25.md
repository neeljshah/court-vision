finding (sol round 2 BLOCKING #2, Opus round 2 BLOCKING #1 and #4) against the
version below the previous revision produced: `in_backoff` was read from
`client.aimd.log[-1][1]` -- the AIMD controller's single shared log across every

order; and `scheduled_work_due()` compared `state["schedule_refusals_total"]`
against a value it remembered from its OWN previous call (`_wedge_prior_refusals`),
so a fresh process (or a first call against an already-nonzero cumulative total)
could report a spurious `due_work_unresolved` even with a zero delta THIS tick.

This revision fixes both by changing what the hook computes and what it passes in,
not by patching the old mechanism:
- **No more `in_backoff` at all.** AMENDMENT 2(a) replaces the shared accumulator
  with a per-ESSENTIAL-SOURCE wedge clock (`WedgeGuard.observe_tick` now takes only
  `client`, `due` and `mono` -- see `local_capture_wedge.py`). A 429 already never
  touches `fail_since_validated` (`local_capture_client.py`'s own per-request
  counter), so a governed backoff neither advances nor resets a source's own clock
  by construction -- there is no separate "was the client in backoff this tick"
  signal left to read, per-source or otherwise, so none is read.
- **The refusals delta is snapshotted by the hook, not remembered by the callee.**
  `_prior_refusals = scheduler.count(state.get("schedule_refusals_total", 0))` is
  the FIRST statement inside `_scheduled_tick`, before `_forward_config(...)` (which
  may bump the counter). The `finally` block then computes
  `refusals_delta = max(0, scheduler.count(state.get("schedule_refusals_total", 0)) - _prior_refusals)`
  and passes it into `wedge.scheduled_work_due(state, now, refusals_delta)`.
  `scheduled_work_due` no longer reads or writes any remembered-prior key.

## Design notes for the future adopter

- **Order-independent (AMENDMENT 2(a)):** `WedgeGuard.observe_tick` reads
  `client.metrics.sources["discovery"]` and `["books"]` directly, every tick, in a
  fixed set order -- never "whichever source's request ran last". Two ticks built
  from the same per-source outcomes in either call order (discovery-then-books vs
  books-then-discovery) now produce byte-identical guard state.
- **429-bounded, not 429-delayed (AMENDMENT 2(a)/5(a)):** a governed backoff
  neither resets nor advances a source's own `fail_since_validated` streak; the
  clock itself is attempt-relative (`last_attempt - failing_since`), so it is
  attempts made DURING a 429 hold (`client.py:64` still counts them) that keep
  moving `last_attempt` -- wall time alone, with no attempts, moves nothing. A
  hold with live requests through it therefore still exits within the bound; a
  429 storm delays nothing, and it also cannot BY ITSELF cause a wedge, since a
  429 never sets `fail_since_validated` above 0 in the first place.
- **Order-correct (AMENDMENT 1(e), unchanged by this revision):**
  `guard.observe_tick(...)` still runs FIRST, inside its own `try`/`except
  SystemExit`, so a `client_wedged` exit is caught rather than propagating
  immediately; `heartbeat()` then runs with `client.metrics.errors` already
  carrying the just-incremented counters, and the per-sport loop's own write reads
  the SAME already-updated `state["hb"][sport]` before the caught exception is
  re-raised in the `finally` block.
- One `WedgeGuard` per client lifetime: stored in `state["_wedge_guard"]` via
  `setdefault`, not persisted/restored across a process restart -- a fresh process
  gets a fresh guard and fresh per-source clocks, which is correct (streak history
  from a dead process is not evidence about a new one).
