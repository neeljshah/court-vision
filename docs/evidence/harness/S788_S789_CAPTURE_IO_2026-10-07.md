## S788 design (scripts/platformkit/ingame/state_shard_index.py, new, 87 LOC)

- Per-path cache: (size, mtime_ns), offset of the last consumed newline, head bytes (256),
  the shard's own fold (latest row per game plus per-line refusal counts), future-row lines,
  and the unterminated tail.
- An unchanged stat with `now >= cached now` means the shard is not opened (0 bytes).
- Growth means only `[offset, size)` is read, in 8 MiB chunks with a carried partial line, so a
  3.75 GB first read is memory-bounded. The old `read_text` held the whole file in memory.
- Any of these triggers a counted full re-read: shrink, mtime going backwards, changed head
  bytes, cached offset no longer after a newline, or `now` going backwards. A missing shard is
  dropped, and shards outside the 2-day window are evicted.
- `polymarket_live_link.state_index` merges each shard's fold with the existing `_keep` rule.
  It re-adds the cached per-line refusal counts on every call (the old code re-counted every
  line per call, and the heartbeat's cumulative `error_counters` keep that meaning). It replays
  future rows and the tail each call. Signature and return shape are unchanged. File is 251 LOC.
- Deviation from the dispatch: the I/O counters (`state_index_bytes_read`, `_full_reads`,
  `_incremental_reads`) are NOT in the errors Counter, because
  `tests/platformkit/execution/soccer_collision_cases_s490.py:56` asserts that Counter is empty
  on a clean archive. Round 1 kept them in a module-global `STATS`; round 2 scopes them per
  client via `state_shard_index.stats(errors)` (see Round 2).

Synthetic bytes per tick (4.01 MB shard, 15 rows appended per tick, 10 ticks):
old = whole shard (4,013,620 to 4,133,815 B per tick); new = 13,611 B per tick (0.33 pct).

## S789 -- BLOCKED (premise false)

The dispatch says that in `_ingest` the "rows before [cutoff] are discarded AFTER parsing" and
asks to bisect so that pre-cutoff rows are never parsed. That reverses the code.
`recover_rows` sets `cutoff = now`. `_ingest` KEEPS every row at or before it and drops only rows
after it (`archive_future_receipts`). `StateWriter.recover_states` needs the latest row per game
at or before now, from both day shards. Skipping pre-cutoff rows would recover nothing, and no
bounded tail is equivalent: a game whose last receipt is early in the shard would be lost.

The measured real cause (probe: synthetic 5,000,554 B tennis-like shard, 6,918 rows, psutil
`io_counters` in-process):
- As landed: read 61,630,458 B (12.3x the shard), 7,535 read ops, which is about 8.9 KB per row.
  The yield loop's `_read` opens the shard per recovered row with default buffering, and the
  BufferedReader fills a full 8 KB buffer for a row of about 720 B.
- Same code with `open(path, 'rb', buffering=0)` in `_read`: identical recovered rows
  (`first == second` True) and 10,001,156 B read (2.00x: one ingest pass plus one exact re-read).
- Live, the ratio was 87.66 GB over 4.47 GB of shards, about 19.6x, plus 31.14 GB written. The
  extra above 12.3x and the writes are NOT measured here. The hypothesis is sqlite page churn at
  `cache_size=-2048` on a multi-million-row receipts table.

PROPOSED re-spec (a new row id, the orchestrator's call): `local_state_recovery._read` opens with
`buffering=0`, which is measured above to give identical rows at 2.00x. Optionally, measure the
sqlite share on the pod against a copy of the 3.75 GB shard. No S789 code is committed.
